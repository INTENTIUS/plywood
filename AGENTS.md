# For agents

- Read CONTRIBUTING.md first. A feature goes in chant CI core when terragucci shares it, else in chant's pulumi lexicon, and plywood holds only its words, presets, config defaults, init templates and docs. Approvals, gate decisions, overrides, applies and runs are rows on the chant workspace ledger, never plywood git writes.
- No module under `packages/plywood/src` runs pulumi, plunge or git. chant runs them in process with plywood's words (`src/words.ts`).
- plywood owns no exit codes. It passes chant's through unchanged; `src/exit-codes.ts` reads chant's table and falls back to the same numbers when the installed chant lacks it.
- `@intentius/chant` and every chant lexicon are pinned to one exact version, the same in the root and package manifests (`just bundle-check` holds the pin). A chant feature newer than the pin goes behind a feature-detect with a working fallback: a lazy `import()` with `@ts-ignore`, and the subpath added to `CHANT_NEXT` in `packages/plywood/scripts/chant-exports.mjs`. The bundle does not carry chant: an `@intentius/chant` import the installed chant serves as compiled JS stays external and runs the pinned package (chant#4591).
- `just chant-local [<chant-dir>|--reset]` builds against a local chant. Go back to the pin with `--reset` before you commit a lock file.
- Before proposing a change, run `just typecheck`, `just bundle-check` and `just test`; for site changes, `just site-lint` and `just site`.
- The CI workflow is declared in `ci/ci.ts`. Edit the TypeScript and run `just ci`; never edit `.github/workflows/ci.yml` by hand, since CI fails when it differs from the render. `pages.yml` deploys the site and stays hand-written.
- Nobody runs `npm publish` or pushes an image by hand, apart from the maintainer's one-time first publish below. Releases go through `.github/workflows/publish.yml` on a `v*` tag.
- The CI workflows are `ci/ci.ts` (ci.yml) and `publish/publish.ts` (publish.yml); `chant-ci-green.yml` is chant's, written by `chant ci workflow --token-secret CI_GREEN_TOKEN` from `chant.workspace.json`'s `ci.green`. `just ci` renders all three.
- Every check runs on local builds, fakes, loopback servers or the floci emulator. Pulumi backends are `file://`, `plunge+file://` or S3 on floci; never a real cloud, Pulumi Cloud or the default Pulumi backend.
- `e2e/` is the bench on chant's e2e harness (plywood#25): plywood's seed, its claims as harness scenarios, and the checks they read from chant's ledger. It reaches `@intentius/chant/e2e-harness` by a lazy import and refuses on a chant without it; `stack/` is the tutorial bench that works on the pin. Neither is part of the package.
- The tagline is "CI Automation for Pulumi", word for word.
- The site is for users and describes plywood as published. Notes about this repo, issue links and build status stay out of it, apart from one page, `site/src/content/docs/reference/development.mdx`, which links the repository docs and lists the draft pages with their issues; contributor material goes in CONTRIBUTING.md. A guide for a feature that needs a newer chant or plunge than the pin stays a draft (`draft: true` with `needs:`).

## Releasing

A release puts both images on GHCR, then `@intentius/plywood` on npm. The npm package names the images by digest (`packages/plywood/src/image-digests.json`), and a digest exists only once the image is pushed, so the order is fixed, as in terragucci:

1. `just release-bump <version>` sets `packages/plywood/package.json`, `package-lock.json` and both Dockerfiles' version label. Add a `## In <version>` section to `site/src/content/docs/reference/whats-new.md` in the same pull request, and merge it to main.
2. `just release <version> --dry-run`, then `just release <version>` (`scripts/release.mjs tag`). It takes the newest green commit of main (`chant ci last-green`, from the `ci/green/<sha>` tags `chant-ci-green.yml` pushes), never a hand-picked one, and checks: the version is X.Y.Z; the commit is on main, at that version, green and not revoked; tag `v<version>` is on neither side; npm has no such version and it is above npm's latest; and, from a clean checkout of that commit, `npm run build`, `bundle-check`, `npm pack` and `npm publish --dry-run` of the packed tarball. Then it tags the commit and pushes only the tag. `--dry-run` (`-n`) runs every check, reports each failure, and creates, changes and pushes nothing. `--commit <sha>` names the commit (it must still be green), and `--skip-green` (or `PLYWOOD_RELEASE_SKIP_GREEN=1`) releases main's tip or the named commit without a `ci/green` tag, for when the tick has not run.
3. On the tag, publish.yml's `test` job runs the package checks, the `images` job pushes `ghcr.io/intentius/plywood-pulumi:<version>-pulumi<v>` and `plywood-plunge:<version>-plunge<v>` for linux/amd64 and linux/arm64 with provenance and an SBOM and prints each reference with its digest, and the `publish` job refuses, since the digests are not recorded yet.
4. `just record-digests <run id>` (the tag's run: `gh run list --workflow publish.yml --branch v<version>`) reads each reference's digest from GHCR, refuses one that differs from the run's log, and writes `image-digests.json`. Merge it to main.
5. Run the publish workflow on main (`gh workflow run publish.yml --ref main`). The images job is skipped off a tag; the publish job skips a version npm already has, refuses a bundle that lacks a digest, and runs `npm publish --provenance --access public` from `packages/plywood`.

The workflow publishes with npm trusted publishing: npm accepts the job's GitHub OIDC token (`id-token: write`), so there is no npm token, and the package carries a provenance statement for the run. It needs npm 11.5.1 or later, which the job installs when Node's bundled npm is older.

The first publish is the maintainer's, by hand, because npm configures a trusted publisher only on a package that exists. From a clean checkout of main, logged in to npm with publish rights on `@intentius`: `npm ci && npm run build && npm run bundle-check -w @intentius/plywood`, then `cd packages/plywood && npm publish --access public`. Then, on npmjs.com, in `@intentius/plywood`'s settings under Trusted Publisher, GitHub Actions: organization `INTENTIUS`, repository `plywood`, workflow filename `publish.yml`, environment empty. The fields are case-sensitive and `repository.url` in `packages/plywood/package.json` must match. npm expires a trusted publisher that has not published within 2 days, so set it up shortly before the first release through the workflow. Once that release works, set the package to require two-factor authentication and disallow tokens. `chant-ci-green.yml` needs the `CI_GREEN_TOKEN` secret to tag commits that change a workflow file.

`plywood upgrade [<version>]` is the user's side of a release: it moves a repository's `@intentius/plywood` and `@intentius/chant*` pins (package.json and `chant.workspace.json`'s `pins`) to the release and the chant it pins, runs `npm install`, and runs the new plywood's `plywood ci`, so one pull request carries the move.
