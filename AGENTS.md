# For agents

- Read CONTRIBUTING.md first. A feature goes in chant CI core when terragucci shares it, else in chant's pulumi lexicon, and plywood holds only its words, presets, config defaults, init templates and docs. Approvals, gate decisions, overrides, applies and runs are rows on the chant workspace ledger, never plywood git writes.
- No module under `packages/plywood/src` runs pulumi, plunge or git. chant runs them in process with plywood's words (`src/words.ts`).
- plywood owns no exit codes. It passes chant's through unchanged; `src/exit-codes.ts` is chant's table (`@intentius/chant/exit-codes`).
- `@intentius/chant` and every chant lexicon are pinned to one exact version, the same in the root and package manifests (`just bundle-check` holds the pin). A chant feature newer than the pin comes with a move of the pin, not a feature-detect: plywood imports what the pinned chant has, and the build fails on a subpath it lacks. The bundle does not carry chant: an `@intentius/chant` import the installed chant serves as compiled JS stays external and runs the pinned package (chant#4591).
- `just chant-local <chant-dir>|--reset` builds against a local chant through `chant dev local`. Go back to the pin with `--reset` before you commit a lock file.
- Before proposing a change, run `just typecheck`, `just bundle-check` and `just test`; for site changes, `just site-lint` and `just site`.
- The CI workflow is declared in `ci/ci.ts`. Edit the TypeScript and run `just ci`; never edit `.github/workflows/ci.yml` by hand, since CI fails when it differs from the render. `pages.yml` deploys the site and stays hand-written.
- Nobody runs `npm publish` or pushes an image by hand, apart from the maintainer's one-time first publish below. Releases go through `.github/workflows/publish.yml`, dispatched by hand with the version.
- The CI workflow is `ci/ci.ts` (ci.yml). publish.yml is chant's, written by `chant release workflow --forge github` from the `release` block in `chant.config.ts`, and `chant-ci-green.yml` is chant's, written by `chant ci workflow --token-secret CI_GREEN_TOKEN` from `chant.workspace.json`'s `ci.green`. `just ci` renders all three.
- Every check runs on local builds, fakes, loopback servers or the floci emulator. Pulumi backends are `file://`, `plunge+file://` or S3 on floci; never a real cloud, Pulumi Cloud or the default Pulumi backend.
- `e2e/` is the bench on chant's e2e harness (plywood#25): plywood's seed, its claims as harness scenarios, and the checks they read from chant's ledger. It runs on `@intentius/chant/e2e-harness`; `stack/` is the tutorial bench. Neither is part of the package.
- The tagline is "Pulumi ops and governance.", word for word.
- The site is for users and describes plywood as published. Notes about this repo, issue links and build status stay out of it, apart from one page, `site/src/content/docs/reference/development.mdx`, which links the repository docs and lists the draft pages with their issues; contributor material goes in CONTRIBUTING.md. A guide for a feature that needs a newer chant or plunge than the pin stays a draft (`draft: true` with `needs:`).

## Releasing

A release is one dispatched run of publish.yml on chant's release block (`release` in `chant.config.ts`), as terragucci's is. It pushes both images to GHCR, publishes `@intentius/plywood` on npm naming them by digest, and creates the GitHub release:

1. Add a `## In <version>` section to `site/src/content/docs/reference/whats-new.md` and merge it to main. Nothing else in the pull request names the version: `packages/plywood/package.json`, `package-lock.json` and the Dockerfiles keep the committed version, and the release build alone carries the label (`release.version` in `chant.config.ts`).
2. Dispatch publish.yml with the version as its label (`gh workflow run publish.yml -f label=<version>`, the bare X.Y.Z). The `gate` job takes the newest green commit at or below main's tip (`chant ci last-green`, from the `ci/green/<sha>` tags `chant-ci-green.yml` pushes). The `cut` job runs `chant release cut` there: it stamps the label into `packages/plywood/package.json` and the lockfile as the package version, builds the package, packs it into `images/pack`, then builds each image as an OCI archive from its Dockerfile (the `release.images` entries in `chant.config.ts`, for linux/amd64 and linux/arm64, with the label as the `CHANT_RELEASE_LABEL` build argument the Dockerfiles read the tarball name and version label from), records their digests, builds the bundle with them (`scripts/build-cli.mjs` reads `CHANT_RELEASE_DIGESTS` and writes `packages/plywood/dist/image-digests.json`), restores the stamped files, records the release on `chant/lifecycle` and pushes the tag `release/<version>`.
3. The `publish` job stamps the label into the package again (`chant release stamp`), checks the cut's archives against the recorded digests, builds the bundle with them again, and runs `chant release publish`: `ghcr.io/intentius/plywood-pulumi:<version>-pulumi<v>` and `plywood-plunge:<version>-plunge<v>`, then the npm package (trusted publishing; the plan refuses a digest in `dist/image-digests.json` the release did not record), then the GitHub release with its notes from the Changes page's `## In <version>` section.

A build outside a release carries no digests, so a pipeline it writes runs in chant's default image with plywood's install lines.

Update `EVIDENCE.md` with each release (`just e2e render` regenerates it from the scenarios and the bench's recorded rows). The docs site does not show claims or recorded runs; EVIDENCE.md is where they live.

The workflow publishes with npm trusted publishing: npm accepts the job's GitHub OIDC token (`id-token: write`), so there is no npm token, and the package carries a provenance statement for the run. It needs npm 11.5.1 or later, which the job installs when Node's bundled npm is older.

The first publish is the maintainer's, by hand, because npm configures a trusted publisher only on a package that exists. From a clean checkout of main, logged in to npm with publish rights on `@intentius`: `npm ci && npm run build && npm run bundle-check -w @intentius/plywood`, then `cd packages/plywood && npm publish --access public`. Then, on npmjs.com, in `@intentius/plywood`'s settings under Trusted Publisher, GitHub Actions: organization `INTENTIUS`, repository `plywood`, workflow filename `publish.yml`, environment empty. The fields are case-sensitive and `repository.url` in `packages/plywood/package.json` must match. npm expires a trusted publisher that has not published within 2 days, so set it up shortly before the first release through the workflow. Once that release works, set the package to require two-factor authentication and disallow tokens. `chant-ci-green.yml` needs the `CI_GREEN_TOKEN` secret to tag commits that change a workflow file.

`plywood upgrade [<version>]` is the user's side of a release: it moves a repository's `@intentius/plywood` and `@intentius/chant*` pins (package.json and `chant.workspace.json`'s `pins`) to the release and the chant it pins, runs `npm install`, and runs the new plywood's `plywood ci`, so one pull request carries the move.
